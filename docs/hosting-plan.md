# 本番のアプリを置く場所の方針

2026年11月15日に決めた案。圭佑の確認待ち。

## 1. 結論
1. 1館目の現場診断（12月中旬〜）は、今のClaudeの共有リンクのままで進める。
2. 試行で実際のスタッフに使ってもらう前に、本番の置き場所に移す。
3. 本番の置き場所は **Google の Firebase（東京リージョン）** にする。
   1. 画面は Firebase Hosting に置く。
   2. 質問や受け入れのデータは Firestore（データベース）に置く。
   3. ログインは Firebase Authentication。
   4. AIは、Cloud Functions（サーバーの小さなプログラム）から Claude API を呼ぶ。APIキーはサーバーにだけ置き、スマホには渡さない。
4. アプリ本体（`src/app.html`）は作り直さない。今は Claude の部品（`claude.use("db")`、`claude.use("sample")`、`claude.use("user")`）を呼んでいるので、同じ呼び方で Firebase と Claude API につなぐ「つなぎの部品」を1つ足す。こうすると、Claudeの共有リンク版と本番版を、同じ本体から作れる。

## 2. なぜ Firebase か
1. 今のアプリのデータの扱い方（コレクション、ドキュメント、変わったらすぐ画面に届く）が、Firestore とほぼ同じ形。つなぎの部品が小さくて済む。
2. 東京リージョンに置けるので、データが日本にある。旅館に説明しやすい。
3. 画面、データ、ログイン、サーバーの小さなプログラムが1か所にそろう。吉田1人で15〜20館を保守する前提に合う。
4. 小さい規模なら、無料の枠に近い費用で動く。使った分だけ払う料金なので、予算の上限の通知を設定しておく。

ほかの候補と見送った理由。
1. Claudeの共有リンクのまま本番にする。スタッフ一人ひとりをClaudeに招待する必要があり、入れ替わりの多い短期スタッフには合わない。旅館向けの自分のサービスとしての見た目も作りにくい。
2. Supabase。性能は十分だが、データの扱い方が今のアプリと違うので、つなぎの部品が大きくなる。
3. 自分でサーバーを借りる（VPS）。保守、更新、障害対応を1人で抱えることになる。

## 3. だれが、どう入るか
1. 新人スタッフ：パスワードなし。受け入れ担当がLINEで送るリンク（宿ごとの招待の合言葉つき）を開くだけで使える。端末ごとに名前のないアカウントを自動で作り、その宿のデータだけに書ける。辞めたら受け入れ担当が止められる。
2. 旅館の管理者：メールに届くリンクでログインする（パスワードなし）。自分の宿のデータだけを見られる。
3. 運営者（吉田）：すべての宿を見られる。外部の相談窓口の声は、運営者だけが読める。

## 4. データの置き方
1. 宿ごとに分ける。`inns/{宿のid}/questions`、`people`、`notices`、`learned`、`proposals`、`cards`、`settings`、`innvoices`、`relays`。
2. 外部の相談窓口の声は `inns/{宿のid}/voices/{本人}`。書けるのは本人、読めるのは運営者だけ。
3. Firestore のセキュリティルールで、ほかの宿のデータは読めないし書けないようにする。今のClaudeの共有版で作ったルール（持ち主だけが読める声）と同じ考え方。
4. 宿の中身（教材、館内、質問係の資料）は、これまでどおり `inns/<id>.json` からビルドで画面に入れる。月1回の更新は、ビルドして載せ直すだけ。

## 5. AIの使い方と費用の見込み
1. 使う場面は、質問係、翻訳、教材づくり、回答案、初日シート、教材に足す案。
2. モデルは Claude Opus 5.5（`claude-opus-5-5`）を基本にする。安いモデル（Sonnet 5.5、Haiku 5.5）に下げるかは、試行で質を比べてから圭佑が決める。
3. 質問係は、毎回同じ「宿の資料」を送るので、プロンプトキャッシュ（同じ部分を安く読み直す仕組み）を使う。
4. 費用の見込み（Opus 5.5、2026年11月の料金、1ドル150円で計算）。
   1. 質問1回は、資料などの入力が1万トークン前後、出力が数百トークン。キャッシュが効けば1回およそ2〜4円。
   2. 1館で月300回質問されると、月およそ1,000円前後。翻訳や教材づくりを足しても、1館あたり月数千円の見込み。
   3. 試行で実際の回数とトークン数を測って、月額料金に入れる。
5. 使いすぎを防ぐため、宿ごとに1日の上限回数をサーバーで決める。
6. AIの処理は海外のサーバーで行われる。利用規約と個人情報の説明に書く。スタッフには、名前や体調などの個人のことを質問に書かないよう案内する（体調などは今も担当者に回す設計）。

## 6. 進め方
1. 第1段階（試行の前まで）
   1. 圭佑が用意するもの：Googleアカウントで Firebase のプロジェクトを作る（従量課金のプランにし、予算の通知を設定）。Anthropic の Console で APIキーを作り、支払い方法を登録する。
   2. こちらで作るもの：つなぎの部品、Cloud Functions（AIの呼び出し、招待の合言葉の確認）、セキュリティルール、宿ごとに載せるビルド。
   3. 載せる場所は、はじめは Firebase の無料のアドレス（`〜.web.app/宿のid/`）。独自のドメインは、名前が決まってから。
2. 第2段階（2館目から）
   1. 運営者の画面（全館の一覧、月次報告の数字）。
   2. 成果の記録（先輩が付いた時間、一人立ちまでの日数、2週間以内の退職）。
   3. LINEとの連携。

## 7. 決めてほしいこと
1. この方針（Firebase）で進めてよいか。
2. AIのモデルは、まず Opus 5.5 で試行してよいか。
3. 本番を作り始める時期（試行の開始日から逆算する）。
